## 下一项实际入口核查

当前MainActivity.provideFlutterEngine调用LocalHost.engine；shouldDestroyEngineWithHost返回false，onDestroy只登记Activity事件并清空activity引用。LocalHost.engine返回cached，首次创建后保存cached；现有recreateActivity只调用Activity.recreate。定点检索当前LocalHost没有engine.destroy/清空cached/销毁engine的测试入口。因此不能把Activity重建命令改名后当作engine死亡测试；此前全进程force-stop也不能隔离engine死亡。

下一小批建议A04/A07「同进程engine销毁后的安全R3退路」，Android优先：

1. 前置重新核对已选35a63609在线/解锁及普通产物，记录当前engine/host/PID和自有播放资源；不依赖本报告推断设备可用。
2. 首先设计并复核专属诊断入口及生命周期通知顺序，再实施。现有方法不存在，文档不提供虚假可运行命令；禁止从正在被销毁的Dart Future等待自身完成。
3. 缺可靠存活权威时采用05 C-03/E2既有R3默认暂停退路，不预设无损R2。销毁前后的底层暂停/释放与旧回调失效必须可观察；原生不新增队列/随机/音质/重试业务。不能只是关Activity或销毁播放器。
4. 验收记录同PID、旧/新engine标识、host和实际资源、协调器新epoch、旧控制权/端点失效；新engine从已保存身份读回且暂停，只有显式继续才重新分配播放资源。若只能整进程死亡，保留“独立engine未验证”，不得改名通过。
5. 预计归属A04 Android维护者+ A07运行时维护者串行整合；候选文件LocalHost/MainActivity、专属probe/集成测试与证据。正式allowlist和真实API顺序在下一批领取时登记；共享冻结如需变化回A02流程，不能静默改哈希。Windows未改时不拿Android结果替代其R2证据。

这只是下一项可实施设计的输入，不在本批创建空壳或修改架构；不要求新手决定类名。若现有同进程宿主不能安全复建，应记录约束并按既有R3退路评审，而非承诺后台永生。
