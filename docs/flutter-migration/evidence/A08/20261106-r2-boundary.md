## 下一实施批次的具体输入

下一批应先由A07与A02同一维护者串行提出窄的单轨接管合同及失败测试设计，再实现消费者。以下是评审清单，不是已冻结的新API或已批准架构：

1. 确定存活边界：先选同isolate内backend存活、协调器对象替换的最小实验。它只证明该实例组合，不能代替跨engine死亡；跨engine需要另外证明身份与权威的存活位置，不引入原生队列业务。
2. 明确权威转移点：旧入口退休、旧准备结果及定时动作失效、新owner生效须有唯一顺序；旧claim/事件/释放动作不能作用于新权威。取消接管与竞争两个接管者必须收敛到一个owner或安全暂停。
3. 核对资源与业务：backend实例/epoch、handle/consumer/resourceRevision、session/entry、generation、transition、confirmation及事件游标必须能交叉验证。持久快照可能落后，不能把最后保存位置覆盖仍活的原生播放状态。确认去重需覆盖接管前后重复playing。
4. 明确快照与事件间隙：读取存活状态时到达的事件、系统pause/stop和迟到prepare必须有处理顺序；不静默丢命令，不让旧订阅释放仍需接管的轨道。两对象同时订阅并各自决策不算排他。
5. 为不匹配/资源已死/接管取消规定有界R3退路；未经实际released凭据不把资源计数归零，不因超时推断物理死亡。旧副本仍可读，默认暂停，只有明确继续才分配新资源。

验收至少区分：正常单轨接管后同资源持续推进且不再prepare/play、不重复确认；异常身份不符转暂停；取消或中途stop不复活；并发旧回调/两个接管者只有一个权威。共享受控测试先建立，再分别验证Android/Windows真实后端，记录新旧对象/epoch和资源实例；轮询两个端点不能证明连续听感或绝对无瞬态。
